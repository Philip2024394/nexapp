## 8. Idempotence on Re-run

### Migration 207
**Fully idempotent.** Uses `ADD COLUMN IF NOT EXISTS` (line 5–7). Re-running adds no new rows; existing columns are left unchanged.

**Evidence:** `/c/Users/Victus/nexapp/nex-supabase/migrations/207_nex_onboarding_and_vault_trial.sql:5–7`

### Migration 257
**Fully idempotent via multiple guards:**

1. **Part 0 (line 30–31):** Aborts if 257 already exists in nex_migration_history.
   ```sql
   IF EXISTS (SELECT 1 FROM nex_migration_history WHERE version = '257') THEN
     RAISE EXCEPTION 'Migration 257 already recorded in nex_migration_history. Aborting.';
   END IF;
   ```

2. **Part 1 (lines 48–199):** Pre-flight exact-definition validation. If any column, constraint, or index has drifted, the transaction aborts and no changes are made.

3. **Part 2 (lines 204–218):** `ADD COLUMN IF NOT EXISTS` on all 9 columns. Already-existing columns are skipped.

4. **Part 3 (lines 224–246):** `CREATE CONSTRAINT IF NOT EXISTS` guards on both table-level CHECKs. Already-existing constraints are skipped.

5. **Part 5 (lines 273–283):** `CREATE INDEX IF NOT EXISTS` on all 3 indexes. Already-existing indexes are skipped.

6. **Part 6 (lines 290–326):** Hardcoded precondition checks. If exactly 2 bisnis rows with sentinel+dated expiries don't exist, the entire migration fails and rolls back. This is intentional · the owner does not want re-runs to silently process different sentinel values.

7. **Part 7 (line 412–418):** `INSERT ... ON CONFLICT DO NOTHING` on the history row (implicit via transaction-level uniqueness).

**However:** The backfill in Part 6 is **NOT** strictly idempotent in the conventional sense. If 257 is somehow re-run after the first bisnis account receives shop_tier='unlimited', the WHERE clause (line 344: `AND shop_tier IS NULL`) will skip that account on the second run, leaving only the second account to be updated. This is a benign state divergence (one bisnis account stays unmigrated), but it differs from "re-running leaves everything in the same state."

**Post-check logic (lines 355–369) catches this in advance:**
```sql
SELECT COUNT(*) INTO v_migrated
FROM nex_account WHERE tier='bisnis' AND shop_tier='unlimited';
IF v_migrated <> 2 THEN
  RAISE EXCEPTION 'Backfill post-check 1 failed: expected 2 rows with shop_tier=unlimited, found %.',
    v_migrated;
END IF;
```

So re-running 257 on a database where only 1 bisnis account has been updated would fail the post-check and roll back the entire transaction, preventing partial data corruption.

**Evidence:** `/c/Users/Victus/nexapp/nex-supabase/migrations/257_nex_account_independent_shop_vault_entitlements.sql:30–31, 48–199, 204–218, 224–246, 273–283, 290–326, 355–369, 412–418`
