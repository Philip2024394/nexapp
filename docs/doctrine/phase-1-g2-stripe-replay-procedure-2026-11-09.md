## 2 · Safety constraints (sealed into the procedure)

### 2.1 What the replay must NOT do

- **MUST NOT create a real customer charge.** Stripe test-mode events only.
- **MUST NOT touch real Stripe production data.** No real customers · no real subscriptions · no real payment intents.
- **MUST NOT leak PII into test payloads.** All metadata fields use obvious dev-only identifiers (`test_business_id` prefix).
- **MUST NOT run against a project pointed at live Stripe keys.** The procedure requires explicit verification that `STRIPE_SECRET_KEY` is a `sk_test_*` key (not `sk_live_*`).
- **MUST NOT be left running afterward.** The Stripe CLI listener is terminated after each replay.

### 2.2 Idempotency + cleanup

- Each replay uses a unique Stripe test event ID (generated by `stripe trigger`)
- Any rows written to `nex_billing_event_log` during the test are TEST ROWS · annotated in the event metadata · can be deleted via a follow-up service-role cleanup (owner-authorised separately)
- Alternative · leave rows in place and tag them clearly · they demonstrate the webhook path works

### 2.3 Non-reversibility of a webhook write

Once the webhook processor writes a row, it's persistent. Cleanup is possible but requires:
- Service-role DELETE from `nex_billing_event_log` for the test rows
- Or leave them with a clear `outcome_detail` indicating the test context
- Either path is a **separate owner-authorised action** · NOT included in G2 replay authorisation

## 4 · The procedure (6 bounded steps)

### Step 1 · Confirm production state is clean before test

```
# Count rows in nex_billing_event_log before the test
# (Expected: 0 per preflight + G2 AFTER evidence)
SELECT COUNT(*)::bigint AS n FROM nex_billing_event_log;
```

Expected result: **0 rows**. If > 0, document the pre-test count so we can distinguish test rows from real traffic.

### Step 2 · Confirm anon-REST cannot read

```
curl -s \
  -H "apikey: $NEXT_PUBLIC_NEX_SUPABASE_ANON_KEY" \
  -H "authorization: Bearer $NEXT_PUBLIC_NEX_SUPABASE_ANON_KEY" \
  "$NEXT_PUBLIC_NEX_SUPABASE_URL/rest/v1/nex_billing_event_log?select=*&limit=5"
```

Expected: HTTP 401 · PostgreSQL error code `42501` permission denied. (Already verified in G2 AFTER evidence.)

### Step 3 · Start Stripe CLI listener forwarding to production webhook endpoint

```
stripe listen --forward-to https://<production-url>/api/nex-native/billing/webhook/stripe \
  --events checkout.session.completed,customer.subscription.created,invoice.payment_succeeded \
  --skip-verify
```

**IMPORTANT:** This forwards to PRODUCTION · ensure the terminal has test-mode Stripe keys only. The `--skip-verify` is for the webhook signature forwarding contract.

Alternative (safer) · forward to a NEX production webhook endpoint that includes test-mode routing (if one exists) · OR skip Step 3 entirely and use Step 4's `stripe trigger` which bypasses forwarding.

### Step 4 · Trigger a safe test event

Use a test-mode payment_intent that does NOT reach a real Connect account:

```
stripe trigger payment_intent.succeeded \
  --override payment_intent:metadata.nex_business_id=test_business_id_g2_replay_$(date +%s) \
  --override payment_intent:metadata.nex_buyer_account_id=test_buyer_g2_replay \
  --override payment_intent:metadata.nex_role=buyer_seller_payment
```

Observe:
- Stripe CLI reports event dispatched
- Stripe CLI reports NEX webhook endpoint accepted the event (expected: HTTP 200 if signature verified · 400 if signature issue)
- Webhook processor logs via Vercel · one log entry per step

### Step 5 · Verify service-role write succeeded

```
SELECT
  stripe_event_id,
  stripe_event_type,
  outcome,
  LEFT(outcome_detail, 100) AS detail,
  received_at::text,
  processed_at::text
FROM nex_billing_event_log
WHERE stripe_event_type = 'payment_intent.succeeded'
  AND outcome_detail ILIKE '%test_business_id_g2_replay%'
ORDER BY received_at DESC
LIMIT 1;
```

Expected:
- One row returned
- `outcome` is `'applied'` (Round 33 buyer-payment handler for `nex_role=buyer_seller_payment` events)
- `outcome_detail` references the test metadata

**T6h-webhook GREEN condition:** a row with matching test metadata is present AND `outcome_detail` reflects the buyer-payment handler path.

### Step 6 · Confirm anon-REST STILL cannot read (post-write)

Repeat Step 2's curl command. Same expected result · HTTP 401. This proves the write did NOT inadvertently grant access to anon-REST.

### Step 7 · Terminate Stripe CLI listener

`Ctrl-C` the `stripe listen` process.

### Step 8 · Decision on test-row cleanup

Owner-choice:
- (a) Leave the test row · it's a 1-row documentation artefact · outcome_detail makes it obviously test
- (b) Delete via service-role SQL · `DELETE FROM nex_billing_event_log WHERE outcome_detail ILIKE '%test_business_id_g2_replay%'` · requires **separate owner authorisation**

## 5 · What this replay does NOT verify

- The webhook-processor's handling of **other** event types (invoice.payment_failed · charge.dispute.created · etc.) · each would need its own test
- Idempotency behaviour (receiving the same event twice) · Stripe CLI doesn't easily replay exactly duplicates
- Rate-limit interaction (the webhook endpoint typically has a webhook-specific rate limit separate from the user-facing rate-limit · verified in a separate workstream)
- Signature verification correctness · if `STRIPE_WEBHOOK_SECRET` is misconfigured the signature fails BEFORE the processor runs · observable as HTTP 400 or 401 · NOT a mig 312 regression

## 6 · Observable outcomes matrix

| Outcome | Interpretation |
|---|---|
| Step 4 reports event dispatched · Step 5 shows one matching row · Step 6 still 401 | **GREEN · V-F1-T6h-webhook complete** |
| Step 4 dispatched · Step 5 shows ZERO rows | Webhook endpoint accepted the event but DID NOT write · investigate (likely signature misconfig or handler-side error · not a mig 312 regression) |
| Step 4 dispatched · Step 5 shows the row BUT outcome is `'error'` | Service-role write succeeded on `nex_billing_event_log` but the buyer-payment handler threw · investigate processor-side · this is NOT a mig 312 failure (RLS/grants work) |
| Step 4 dispatched · Step 5 blocked by RLS (service-role query returns nothing) | **RED · mig 312 regression** · service-role no longer has SELECT · highly unexpected · rollback discussion |
| Step 6 returns 200 with data | **RED · mig 312 regression** · anon now sees data · rollback immediately |
